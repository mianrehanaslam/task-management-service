# Task Management Service

REST APIs for creating, reading, updating and deleting tasks, stored in an H2 in-memory database
(Jira [DS-6622](https://servicemarket.atlassian.net/browse/DS-6622)).

- Java 17, Spring Boot 3.2.12 (Spring Web, Spring Data JPA, Bean Validation), H2
- Layers: `controller` → `service` → `repository` → `entity`, with request/response DTOs in `dto`
  and a single `@RestControllerAdvice` in `exception`

## Running locally

Requires JDK 17+. The Maven wrapper downloads Maven 3.9.9 on first use.

```bash
./mvnw spring-boot:run -Dspring-boot.run.profiles=local
```

or build and run the jar:

```bash
./mvnw clean package
java -jar target/task-management-service-0.0.1-SNAPSHOT.jar --spring.profiles.active=local
```

The API is served on `http://localhost:8080/api/tasks`.

### H2 console (local profile only)

With the `local` profile active, the console is at `http://localhost:8080/h2-console`
(JDBC URL `jdbc:h2:mem:tasksdb`, user `sa`, empty password). It only accepts connections from
the local machine. Without the `local` profile the console is disabled and returns `404`.

The H2 console can run arbitrary SQL, so never activate the `local` profile on a shared or
internet-facing host.

### Data lifetime

The database is in memory, so all tasks are lost when the application stops.

## Configuration

| File | Purpose |
| --- | --- |
| `application.properties` | Base/production-safe settings: H2 console off, Hibernate `ddl-auto=validate` (never drops or recreates tables), no stack traces or exception messages in error responses. |
| `application-local.properties` | Local development only: named in-memory database, throwaway `sa` credentials, H2 console on. |
| `schema.sql` | Creates the `tasks` table with `CREATE TABLE IF NOT EXISTS` (non-destructive). Runs automatically for embedded databases. |

## API

| Method | Path | Success | Errors |
| --- | --- | --- | --- |
| `POST` | `/api/tasks` | `201 Created` + `Location` header + task | `400` |
| `GET` | `/api/tasks[?status={status}]` | `200 OK` + array (empty `[]` when none), ordered by `id`; optionally filtered by status | `400` (unsupported `status`) |
| `GET` | `/api/tasks/{id}` | `200 OK` + task | `400` (non-numeric id), `404` |
| `PUT` | `/api/tasks/{id}` | `200 OK` + updated task | `400`, `404`, `409` |
| `DELETE` | `/api/tasks/{id}` | `204 No Content` | `400` (non-numeric id), `404`, `409` |

### Task fields

| Field | Type | Rules |
| --- | --- | --- |
| `id` | number | Generated by the database; ignored if sent in a request |
| `title` | string | Required, not blank, at most 150 characters |
| `description` | string or `null` | Optional, at most 1,000 characters |
| `status` | string | Required, exactly one of `PENDING`, `IN_PROGRESS`, `COMPLETED` (case-sensitive) |
| `createdAt` | ISO-8601 UTC timestamp | Set on create; never changes; ignored if sent in a request |
| `updatedAt` | ISO-8601 UTC timestamp | Set on create and on every update; ignored if sent in a request |

`PUT` is a full replacement: every editable field must be sent, and an omitted `description`
is stored as `null`.

### Filtering by status

`GET /api/tasks` takes an optional `status` query parameter:

| Request | Result |
| --- | --- |
| `GET /api/tasks` | All tasks (unchanged behaviour) |
| `GET /api/tasks?status=PENDING` | Only `PENDING` tasks |
| `GET /api/tasks?status=IN_PROGRESS` | Only `IN_PROGRESS` tasks |
| `GET /api/tasks?status=COMPLETED` | Only `COMPLETED` tasks |
| `GET /api/tasks?status=COMPLETED` when none match | `200 OK` with `[]` |
| `GET /api/tasks?status=INVALID` | `400 Bad Request` with a field error for `status` |

Rules:

- The value must be exactly `PENDING`, `IN_PROGRESS` or `COMPLETED`, case-sensitive, the same as
  in request bodies.
- These are rejected with `400`:
  - lowercase values (`pending`);
  - a blank value (`?status=`);
  - padded values.
- The rejected value is never echoed in the response.
- Filtering is done in the database (`WHERE status = ? ORDER BY id`, backed by the
  `idx_tasks_status_id (status, id)` index).
- A repeated parameter (`?status=PENDING&status=COMPLETED`) is rejected with the field error
  `"must be specified only once"`.
- Only the parameter name `status` is recognised. Other query parameters, including `STATUS` or
  `state`, are ignored, as for any other unknown parameter, so a misspelled name returns every task.

```bash
curl 'localhost:8080/api/tasks?status=PENDING'      # 200, only PENDING tasks (or [])
curl -i 'localhost:8080/api/tasks?status=INVALID'   # 400, response below
```

Response to `?status=INVALID`:

```json
{
  "timestamp": "2026-11-02T11:05:27.931242Z",
  "status": 400,
  "error": "Bad Request",
  "message": "Validation failed",
  "path": "/api/tasks",
  "fieldErrors": [
    {"field": "status", "message": "must be one of: PENDING, IN_PROGRESS, COMPLETED"}
  ]
}
```

### Examples

```bash
curl -i -X POST localhost:8080/api/tasks -H 'Content-Type: application/json' \
  -d '{"title":"Complete project documentation","description":"Add setup and API usage instructions","status":"PENDING"}'
```

```http
HTTP/1.1 201
Location: http://localhost:8080/api/tasks/1

{"id":1,"title":"Complete project documentation","description":"Add setup and API usage instructions",
 "status":"PENDING","createdAt":"2026-11-02T10:12:42.356692Z","updatedAt":"2026-11-02T10:12:42.356692Z"}
```

```bash
curl -X PUT localhost:8080/api/tasks/1 -H 'Content-Type: application/json' \
  -d '{"title":"Complete API documentation","description":"Add request and response examples","status":"IN_PROGRESS"}'
curl localhost:8080/api/tasks
curl 'localhost:8080/api/tasks?status=IN_PROGRESS'
curl localhost:8080/api/tasks/1
curl -i -X DELETE localhost:8080/api/tasks/1
```

### Error responses

Every error uses the same body. `fieldErrors` is present only for validation failures, and all
invalid fields are reported together.

```json
{
  "timestamp": "2026-11-02T10:12:42.767840Z",
  "status": 404,
  "error": "Not Found",
  "message": "Task with ID 25 was not found",
  "path": "/api/tasks/25"
}
```

```json
{
  "timestamp": "2026-11-02T10:12:42.691493Z",
  "status": 400,
  "error": "Bad Request",
  "message": "Validation failed",
  "path": "/api/tasks",
  "fieldErrors": [
    {"field": "title", "message": "must not be blank"},
    {"field": "status", "message": "must be one of: PENDING, IN_PROGRESS, COMPLETED"}
  ]
}
```

| Status | When |
| --- | --- |
| `400` | Validation failure, unsupported `status` filter, malformed JSON (`"Malformed request body"`), wrong JSON type for a field, non-numeric id |
| `404` | Task not found, or unknown route (fixed message, request input is not echoed) |
| `405` / `406` / `415` | Unsupported HTTP method / `Accept` type that excludes JSON / request content type. Message is fixed: `"Request could not be processed: <reason>"` |
| `409` | The task was updated or deleted by another request at the same moment (optimistic locking); re-read and retry |
| `500` | Unexpected error; the body only says `"An unexpected error occurred"` and details are logged server-side |

## Tests

```bash
./mvnw clean verify
```

- `TaskServiceTest`: unit tests for business logic (Mockito, fixed clock)
- `TaskRepositoryTest`: JPA persistence against H2 (`@DataJpaTest`)
- `TaskControllerIntegrationTest`: full API behaviour, validation and error format against H2
- `GlobalExceptionHandlerTest`: 409 and 500 mapping, no leakage of internal details
- `TaskRequestTest`: the status rule stays in sync with the `TaskStatus` enum
- `TaskManagementApplicationTest`: startup with the `local` profile; H2 console off by default

The build compiles with `-Xlint:all -Werror`.

## Limitations

- No authentication or authorization (out of scope for DS-6622). Do not expose this service
  publicly as-is.
- No pagination: `GET /api/tasks` returns every task (or every task with the requested status).
- Concurrent writes to the same task are protected by an internal optimistic-lock `version` column:
  the losing request gets `409` instead of silently overwriting. The version is not exposed in the
  API, so there is no `If-Match`/ETag support for edits made across separate read-then-write requests.
- Two simultaneous `DELETE`s of the same task may return `204` and `409` (rather than `204` and `404`).
- Requests that Tomcat rejects before they reach Spring (e.g. illegal characters in the URL) get
  Tomcat's default error page, not the JSON error body.
- Scalar values are coerced by Jackson (for example `"title": 123` is stored as `"123"`), and
  unknown JSON properties are ignored.
- Storage is in memory only.
